## 什么是 goroutine？

goroutine 是 Go 里的**轻量级线程**。

和操作系统线程（thread）相比：

- 创建成本低（初始栈 2KB 左右）
- 切换由用户态调度完成
- 可以轻松创建几十万级别
- 线程是内核调度，goroutine 是用户态调度

Go 不直接把 goroutine 交给内核线程调度，而是自己实现了一套 **GMP 调度模型**。

## GMP

G(groutine):轻量级协程, 2KB栈空间,随着需求增长

M(machine): 操作系统内核线程,是真正干活的人,一般 M>= P

P(processor):调度器或者处理器,每个 P 有一个本地队列（run queue）,P 的数量默认等于 CPU 核数（GOMAXPROCS）

G 必须绑定到 P
 P 再绑定到 M
 M 才能执行 G

为了不让M闲着,调度过程是:

1. 每个 P 有一个本地 G 队列,新创建的 goroutine 优先放入当前 P 的本地队列,调度时优先从本地队列取任务.这样可以减少锁竞争。

2. 如果当前队列满了,或者负载不均衡,就把部分g 放入全局队列

3. 某个p本地队列空了,去全局队列或者其他队列偷一半G来执行,`避免 P 空转`.

   提高cpu利用率

4. 当某个g发生阻塞,比如读写磁盘,M会被阻塞,P会解绑该M,然后寻找一个新的M进行执行剩下的g. 防止一个阻塞不会拖垮整个调度器

5. 抢占式调度. 防止一个g运行时间过程过长导致其他g饿死,运行的时候有监控线程,超过10ms会发出抢占信号,让出cpu

## Channel

Channel（通道）是用于在goroutines之间进行通信的一种机制。通道提供了一种并发安全的方式来进行goroutines之间的通信。通过通道，可以避免在多个goroutines之间共享内存而引发的问题，因为通道的读写是原子性的。

channel 底层是由环形缓冲区 + 发送/接收等待队列 + 锁组成,无缓冲 channel 是同步通信，有缓冲 channel 是异步队列

用途:

- **数据传递：** 主要用于在goroutines之间传递数据，确保数据的安全传递和同步。

- **消息传递：** 适用于通过消息进行事件通知的场景。

- **同步执行：** 通过Channel可以实现在不同goroutines之间的同步执行，确保某个goroutine在另一个goroutine完成某个操作之前等待。

- **多路复用：** 使用`select`语句，可以在多个Channel操作中选择一个非阻塞的执行，实现多路复用。

  

如何处理阻塞:

1. 缓冲通道，在创建通道时指定缓冲区大小，即创建一个缓冲通道。当缓冲区未满时，发送数据不会阻塞。当缓冲区未空时，接收数据不会阻塞。

2. `select`语句用于处理多个通道操作，可以用于避免阻塞。

3. 使用`time.After`创建一个定时器，可以在超时后执行特定的操作，避免永久阻塞。

4. `select`语句中使用`default`分支，可以在所有通道都阻塞的情况下执行非阻塞的操作

   ```go
   func demo() {
   	ch := make(chan string)
   
   	// 模拟 1 秒后发送数据
   	go func() {
   		time.Sleep(1 * time.Second)
   		ch <- "hello"
   	}()
   
   	timeout := time.NewTimer(3 * time.Second)
   
   	for {
   		select {
   
   		// 2️⃣ 正常 select 多路监听
   		case msg := <-ch:
   			fmt.Println("received:", msg)
   			return
   
   		// 3️⃣ 超时控制
   		case <-timeout.C:
   			fmt.Println("timeout, exit")
   			return
   
   		// 4️⃣ default 非阻塞
   		default:
   			fmt.Println("no data yet")
   			time.Sleep(300 * time.Millisecond)
   		}
   	}
   }
   
   ```

   死锁什么时候发生？

   当：所有 goroutine 都在等待 channel并且没有可运行 G,runtime 会检测到死锁

## Defer

`defer` 用于：延迟执行函数，直到当前函数返回时执行

场景:关闭文件,释放资源,解锁

defer 语句执行时，参数立即求值,函数体延迟执行

```go
func main() {
	x := 10
	defer fmt.Println(x)
	x = 20
}
```

输出10

panic 时 defer 会执行吗?

执行顺序：触发 panic,执行当前函数的 defer,向上层函数传播,每层执行 defer

这也是 recover 能生效的原因。

## map和 slice

slice是引用类型，任何对Slice的修改都会影响原始Slice,但是如果在函数内部进行扩容操作,会分配新的底层数组,但原始slice不会引用新的数组

### slice扩容:

append, 导致切片长度超过当前容量时，Go 底层会为切片分配一个新的、容量更大的底层数组，将原数组的数据复制到新的数组中，`并更新切片的指针和容量信息.而旧数组则会被垃圾回收(如果没有其他引用)`，返回指向新数组的切片，同时更新切片的长度和容量。

容量小于 1024的时候,新容量通常是当前容量的两倍

当容量较大时，扩容的增量约为当前容量的 25%

### slice为什么采用**采用倍增策略**?

每次扩容都需要分配新数组并拷贝数据。如果每次只增加固定大小，会导致频繁的内存分配和数据迁移，性能较低。

### slice扩容注意事项

切片本身是线程安全的，但扩容可能导致数据竞争，尤其是当多个 Goroutine 同时访问切片时，需要使用锁或其他并发控制机制。

### map扩容

负载因子 ≈ 6.5  ||  overflow 桶太多  ———— 二倍扩容

负载因子>=6.5: 桶快满了      ———— 等量扩容

 overflow 桶太多：说明哈希冲突严重，不停地插入又删除，导致桶里面虽然元素少，但分布极散，内存碎片严重

### map 并发

原因：map 扩容和写操作不是原子操作

俩种方法：

`sync.Map` ：俩个map：read（只读，原子访问），dirty（写入使用）

var m map[string]int 和var mu sync.Mutex：写多时更合适

关于sync.Map：读优先从 read 读（无锁），写入时加锁更新 dirty，当 dirty 达到一定条件，提升为 read

## ACID

事务四大特性：

A：atomicity：原子性：如果事务中有任何一步操作失败，整个事务的结果都会被撤销，数据库回到事务开始之前的状态。通过这个回滚日志来完成的

**C**: Consistency（一致性.）：事务操作的所有数据必须符合定义好的规则，如外键、主键、检查约束等。通过其他三个特性完成的

**I**: Isolation（隔离性）：隔离性指的是一个事务的执行不受其他事务的干扰。多个事务并发执行时，它们之间应该是隔离的，不会互相影响。通过多版本并发控制或者锁机制来完成的

**D**: Durability（持久性）：持久性指的是一旦事务提交，事务的结果就会永久保存到数据库中，任何系统崩溃或故障都不会丢失已提交的事务数据。通过重做日志完成的

## 事务隔离级别

脏读：一个事务读取另一个事务未提交的数据。

不可重复读：在同一个事务中，多次读取相同的数据可能得到不同的结果

幻读：多个事务读取范围内的数据时，数据数量可能发生变化。

### **Read Uncommitted**（读未提交）

三种情况都会发生

场景：

- 对一致性要求不高，但对性能要求较高的场景。
- 比如日志记录。

### **Read Committed**（读已提交

不会出现脏读

场景：

适用于大多数业务场景，比如：电商网站的商品信息查询。

### **Repeatable Read**（可重复读）

还是会出现幻读：同一个事务内，查询的数据范围内的记录数可能发生变化（例如其他事务插入了新记录）。

场景：

数据分析

### Serializable

三种情况都避免

场景：

金融类系统、银行转账、票务系统

## 索引

### 什么是索引？

**索引**是数据库用来加速查询操作的一种数据结构，类似于书籍的目录。它通过 **减少扫描的数据量**，提高查询效率。

------

### 索引的基本原理

- **索引**是为了加速查询而设计的结构，但它也有代价：
  - **空间代价**：存储索引本身需要额外的存储空间。一个索引对应的就是一棵 B+树，每一个节点都是一个 16KB 大小的页。**占用的空间较大**。
  - **写操作代价**：每次插入、更新或删除数据时，索引也需要更新。

### 索引结构

MySQL 主要使用 **B+ 树** 作为索引的数据结构，常见的索引有：

- **主键索引**（Primary Key）
- **唯一索引**（Unique Key）
- **普通索引**（Index）没有唯一性要求
- **全文索引**（Full-Text Index）文本搜索，而非精确匹配
- **联合索引**（Composite Index）

B+ 树是自平衡的 **树状数据结构**，使得索引查找、插入、删除都保持在对数级别（O(logN)）。

### 什么时候需要创建索引

- 频繁用于查询的列需要创建索引
- 频繁使用排序和分组的列：如果某列经常用于 ORDER BY 或 GROUP BY 子句可以创建索引
- 唯一性要求：主键列和唯一性约束的列会自动创建唯一索引，但如果查询中经常包含唯一性条件，可以额外创建唯一性索引。
- 大表：对于很大的表，建立索引可以提高查询速度
- 连接表的外键列：为外键列创建索引可以提高连接的效率。

### 什么时候不需要创建索引

很少用于查询的字段

经常进行更新的字段不需要创建索引

字段中存在大量重复数据，不需要创建索引，比如性别字段

小表：在小表上，索引不会带来显著的性能提升，还会增加维护开销



### 索引优化

- 前缀索引优化：使用某个字段中字符串的前几个字符建立索引，从而减小索引字段大小
- 覆盖索引优化：从二级索引中可以查询得到记录，避免回表
- 主键索引最好是自增的；这样每次插入一条新记录，都是追加操作，不需要重新移动数据，而使用非自增主键会导致插入主键的索引值是随机的，这可能会插入到现有数据页的某个位置，导致其他数据的移动，造成页分裂。
- 避免过多的索引

### MySQL为什么使用B+树来作索引？

磁盘读写代价更低:只有非叶子节点存储指针，叶子结点全部用来存储数据，磁盘存储压力小

查找效率更稳定：每个数据查找路径都差不多，需要到根节点去查询，而且它阶数更多，路径更短（矮胖树）

便于扫库和区间查询：它的叶子节点是一个双向链表

### 说一下索引失效的场景？

- **使用左或者左右模糊匹配**：比如`LIKE '%abc'` 这样的查询会导致索引失效。
- **在索引列上使用函数或表达式**： 索引列上参与计算，索引失效

```
SELECT * FROM table WHERE UPPER(column) = 'VALUE';
```

- 在 WHERE 子句中，如果在 OR 前的条件列是索引列，而在 OR 后的条件列不是索引列，那么索引会失效。
- 违背最左匹配原则，索引失效
- **数据分布不均匀：** 如果数据分布不均匀，例如某个索引列的大多数值都相同，选择性降低，导致索引失效。
- **隐式类型转换：** 如果查询中的条件涉及到隐式类型转换，例如将字符串与数字比较，索引可能无法被使用。
